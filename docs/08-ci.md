# 08 — CI

`.github/workflows/build.yml`. **Never executed yet.**

## Job graph

```
probe (4 runners, ~1 min each)
  │
  ├─► build            linux-64 · osx-64 · osx-arm64 · win-64      (native, hours)
  │
  └─► build-win-arm64  on windows-latest, cross-compiles           (hours)
            │
            └─► validate-win-arm64  on windows-11-arm              (~1 min)
```

## Why one runner per OS

Cross-OS building is impossible with the conda-forge zig packages — the
`zig_<target>` package for a given OS is only published into that OS's subdirs.
See the table in [05](05-platform-matrix.md). There is no way to compress the
matrix.

| target | runner | why that one |
|---|---|---|
| linux-64 | `ubuntu-latest` | native |
| osx-64 | `macos-13` | last Intel image GitHub offers |
| osx-arm64 | `macos-14` | Apple Silicon |
| win-64 | `windows-latest` | native |
| win-arm64 | `windows-latest` → `windows-11-arm` | cross-build then validate; see below |

macOS is built natively on both architectures rather than cross-built from one.
Cross osx-64 ↔ osx-arm64 is available and would save a runner, but native builds
let the package tests actually run the compiler, which for a compiler is the
point.

## The probe gate

`probe` runs first on every target and takes about a minute. It answers "does
`zig c++` work on this runner, and what C++ runtime does it link" before any job
commits to a multi-hour build. Given that stage 1 can approach GitHub's 6-hour
job cap, a cheap gate is worth a lot.

On Windows the probe additionally prints `zig cc -v`'s `Target:` line and the
DLL imports of a test binary — the data that settles **open question W1**
([09](09-risks-and-open-questions.md)). Read it from the first successful run
and record it in [10-status-log.md](10-status-log.md).

## win-arm64: cross plus a separate validation job

`zig_win-arm64` exists **only in the win-64 subdir**, so a win-arm64 runner
cannot build for itself even natively. The `build-win-arm64` job therefore runs
on `windows-latest` (x86_64) and cross-compiles all three stages.

Two consequences the workflow has to handle explicitly:

1. **It rewrites `llvm_targets_to_build` to `X86;AArch64` before stage 1.**
   Stage 3 uses the *native win-64* `flang.exe` as `CMAKE_Fortran_COMPILER` to
   compile the arm64 runtime. The default `Native` gives an X86-only flang,
   which cannot emit arm64 code. The rewrite is a `sed`-equivalent in PowerShell
   rather than a second variant file, to keep the default fast for everyone else.

2. **The cross job cannot test what it built.** A win-arm64 binary does not run
   on the win-64 host. `validate-win-arm64` downloads the channel artifact,
   runs on `windows-11-arm`, installs the packages and compiles + runs
   `tests/hello.f90`. That job is the only real evidence win-arm64 works.

## Timeouts and the 6-hour cap

`timeout-minutes: 350` sits just under GitHub's hard 6-hour job limit. If stage 1
alone starts approaching it:

- split stage 1 into its own job and pass `channel/` between jobs as an artifact
  (the layout already supports this — each stage only needs the previous
  stage's channel), or
- move to a larger runner, or
- trim `llvm_targets_to_build` further.

The staged design exists partly for this: three jobs of two hours are fine where
one job of six is not.

## Caching

`prefix-dev/setup-pixi` caches the pixi environment (the zig toolchain, cmake,
ninja), which is minutes. It does **not** cache the LLVM build tree, which is
hours.

If iteration speed becomes the bottleneck, the highest-value change is caching
the *stage 1 package* rather than the build tree: key an `actions/cache` entry
on `hashFiles('packages/llvm-zig/recipe/**')` plus the LLVM version and restore
`channel/`. Stage 1 changes rarely once it works, and skipping it turns a
six-hour matrix into a one-hour one.

## Artifacts

Every build job uploads `channel/` with `if: always()`, so a failed run still
yields whatever was produced before the failure. 14-day retention.

## Not wired up

- Publishing to prefix.dev or anaconda.org. `pixi publish --to` already supports
  both; it is a credentials-and-policy decision, not a technical one.
- Scheduled builds. Add a `schedule:` trigger once the matrix is green.
- linux-aarch64. `ubuntu-24.04-arm` runners exist; add a row once linux-64 works.
