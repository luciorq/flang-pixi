# 08 — CI on GitHub-hosted runners

`.github/workflows/build.yml` + `.github/actions/stage/action.yml` +
`scripts/ci-smoke.sh`. Rewritten 2026-09-17 (phase 1 of the plan in
[15 §3](15-landscape-review-2026-09.md)); the previous single-job-per-platform
workflow was never green (its one run was cancelled at 24 h).

## What GHA is for here, and what it is not

The repository is public, so standard runners are free and unlimited. They
are small, though:

| label | vCPU | RAM | our use |
|---|---|---|---|
| `ubuntu-24.04` | 4 | 16 GB | linux-64 (measurement first; gamma is faster) |
| `ubuntu-24.04-arm` | 4 | 16 GB | **linux-aarch64, native** — hardware we do not own |
| `macos-15-intel` | 4 | 14 GB | osx-64 (measurement; omicron/Rosetta is the production path) |
| `macos-15` | 3 (M1) | **7 GB** | osx-arm64 — poor fit; omicron stays the build host |
| `windows-2025` | 4 | 16 GB | win-64 (measurement), and the win-arm64 cross host |
| `windows-11-arm` | 4 | 16 GB | **win-arm64 validation** — the only place those packages run |

Hard job cap: 6 h. Advertised disk: 14 GB (Linux reclaims ~30 GB by deleting
preinstalled SDKs; the census job prints the real numbers per label).

So: GHA is the production path for **linux-aarch64** and for **validating
win-arm64**, the publish step, and cheap PR gates. For linux-64, osx-64,
osx-arm64 and win-64 the self-hosted machines (gamma, omicron, kappa) remain
primary until a measured GHA run of stage 1 lands comfortably under the cap.
Measured reference points: llvm-zig 23.1.1 took 36 min on gamma and about
70 min on omicron; expect 3–5 h on a 3–4 core runner.

## Job graph

```
plan ──► llvm ──► lld ──► flang ──► flang-rt ──► smoke ──► publish (manual)
          (one job per stage per target; channel handed over as an artifact)
census (all six labels: cores/RAM/disk + stage-0 probe; PRs run only this)
cross-win-arm64 (windows-2025, after win-64 flang-rt) ──► validate on windows-11-arm
```

- **Targets are an input** to `workflow_dispatch` (default `linux-aarch64`).
  `win-arm64` implies `win-64`. Pull requests run census only.
- **Every stage is its own job**, so the 6 h cap applies per stage, and a
  failed stage 2 does not throw away stage 1.
- **Hand-off**: each job restores `build-out/<subdir>` from the
  `channel-<target>` artifact, runs standalone `rattler-build` with
  `-c file://…/build-out -c conda-forge --output-dir build-out` (rattler-build
  re-indexes the subdir), drops `bld/` and `src_cache/`, and re-uploads.
  14-day retention.
- **Standalone rattler-build, not `pixi publish`**: pixi publish panics on
  cross targets (docs/12 draft 1) and the pixi-build backend reports
  `build_platform == target_platform` even when cross, which is why the
  recipes' cross conditionals were switched to `build_platform !=
  target_platform` on 2026-09-17 (also what makes a *native* linux-aarch64
  build resolve `zig_linux-aarch64` instead of the cross setup).
- **osx-arm64** sets `FLANG_PARALLEL_COMPILE_JOBS=1` for the 7 GB runner.
- **win-arm64** is cross-built on `windows-2025` from the `channel-win-64`
  artifact (tblgen + the win-64 flang for the runtime) with `--test skip`,
  then `validate-win-arm64` installs the result on `windows-11-arm` and runs
  `tests/*.f90`.
- **smoke** (`scripts/ci-smoke.sh`) creates a throwaway pixi workspace with
  the artifact as first channel, installs `flang-zig flang-rt-zig`, compiles
  and runs every `tests/*.f90` at -O2.
- **publish** only on `workflow_dispatch` with `publish: true`, uploads
  `lld-zig`/`flang-zig`/`flang-rt-zig` of the built targets to prefix.dev
  `universe` with `--skip-existing`; never `llvm-zig`. Needs the repo secret
  `PREFIX_API_KEY` (a `pfx-…` key with write scope on universe).

## First run checklist

1. Add `PREFIX_API_KEY` as a repository secret.
2. Dispatch with defaults (census + linux-aarch64). Read the census summary
   for real free-disk numbers per label, and the stage timings.
3. If the aarch64 chain is green, dispatch again with `publish: true`.
4. Then try `targets: linux-64` once to measure stage 1 on a 4-core x86
   runner; decide from the timing whether win-64/osx-64 are worth moving.

## Not done / later

- Caching LLVM objects (sccache) to make retries incremental — the 10 GB
  repo cache cap fits two or three platforms, not six.
- Self-hosted runners on omicron/kappa would unify both worlds; GitHub
  advises against them on public repos (fork PRs can run code). Only with
  `workflow_dispatch`-only triggers on `main`, if at all.
- Scheduled rebuilds.
