# 17 — zig 0.17.0: is it time, and what changes for us

*Written 2026-10-02, the day after the `0.17.0` tag landed on Codeberg
(commit `7647adab80`, 2026-10-01). No release notes exist yet (ziglang.org
404, no draft in the www repo), so everything below comes from (a) the
tag-to-tag source diff (0.16.0 → 0.17.0) read by six agents and adversarially
verified per impact, (b) the conda-forge zig-feedstock `dev` branch (0.17
master snapshot `2320+1e770dbef`, build 23200, `zig_dev` label only) and (c)
compile probes of that snapshot on gamma (linux-64, cross to Windows) and
omicron (osx-arm64). The verification pass was cut short by usage credits:
every flang-pixi impact below was checked by two refuters; r-zig-pixi items
RZ-01…RZ-06 were, the rest were not (marked). Evidence files live in the
session scratchpad `z17/` (diffs, commit lists, feedstock branches).*

## 1. Verdict

**Yes — look now, change nothing yet.** Looking means: know what 0.17 changes
on our surfaces (done, below), run the probe battery on the `zig_dev`
snapshot (mostly done), and prepare the consumer. Do not bump pins and do
not rebuild chains on a snapshot: conda-forge has **no main-label 0.17**,
only master snapshots whose version string is always `0.17.0` with the
snapshot number in the build string, so a pin like `zig 0.17.*` would not
distinguish snapshot from release. Our rule from docs/13 stands: a zig
version bump is one chain-wide rebuild of all six subdirs with every
validation re-run. The trigger is the first `zig_impl_*` 0.17.0 package on
conda-forge's main label; nothing on the feedstock announces a date.

## 2. What 0.17 changes that we depend on

| surface | 0.16 | 0.17 (tag) / conda-forge dev track | effect on us | status |
|---|---|---|---|---|
| bundled LLVM/clang/lld, libc++ | 21 / 21.1 | **22 / 22.1.8** | compiler-version bump under unchanged LLVM 23 sources: the usual risk of new warnings-as-errors or codegen differences; nothing specific found | rebuild + full CI is the test |
| shared-libc++ preference (docs/16 D1) | feedstock patch, native links, probes `<lib>/../../lib` | **still applied**; dev copy probes an extra `../../lib/zig-llvm/lib` first; `libcxx 22.*` is a run dep of `zig_impl_osx-*`; `ZIG_LIB_DIR` still honoured and now listed by `zig env` | the mirror keeps working — **measured** on the snapshot with `libcxx` present: static libc++ via the mirror, shared without | harden the mirror's sanity check to also reject `../../lib/zig-llvm/lib/libc++*` |
| Linux glibc floor (docs/13) | `<arch>-linux-gnu.2.17`, stubs from abilists | triple grammar identical; default glibc stays 2.31; stubs regenerated from **glibc 2.44** abilists | **measured**: `-target x86_64-linux-gnu.2.17` still yields GLIBC_2.2.5 ceiling and the pre-2.34 split libs; the ceiling tripwire stays the oracle | none |
| macOS default floor (docs/16 D4) | version-less `aarch64-macos` → 13.0 | **→ 15.0** (std.Target default range 15.0–27.0) | the flang-rt shim (`aarch64-macos.11.0-none`) is more necessary, not less — **measured**: wrapper translation of the conda triple now stamps `minos 15.0`; the zig-form triple still gives 11.0 | fix the "13.0" comments; consider the same conda-triple rewrite in flang-zig/lld-zig so no path depends on wrapper translation |
| macOS SDK / `-framework` / `-mmacos-version-min` | native: implicit LC_RPATH per `-L`; pinned target loses SDK | same, resolved by new frontend code | **measured** on the snapshot: `-target aarch64-native.13.0` + `-F$SDK/System/Library/Frameworks -L$SDK/usr/lib` links CoreFoundation at minos 13.0 with no rpath; `-mmacos-version-min` on a native target still ignored; `-fuse-ld=lld` "unused" (zig's own Mach-O linker) | nothing for us; r-zig-pixi's `native.<min>` recipe survives 0.17 |
| Windows CRT (mingw-w64) | 13.0 | **15.0**; new `-D__CRT__NO_INLINE` on every MinGW compile; `zig cc` still links COFF through **lld-link** (the 313 KB self-hosted COFF linker is opt-in) | silent codegen change (header inlines become libcalls into zigc/compiler-rt); our CRT snapshot in flang-rt-zig must be re-harvested from zig's own cache in the 0.17 wave | rebuild + Windows CI |
| aarch64 `wcstold` shim | missing from zig's aarch64 CRT (feedstock packaging defect) | **measured fixed** on the dev snapshot: links, imported from `api-ms-win-crt-convert` | the `wcstold_compat.c` shim becomes redundant on 0.17 (keep until the win-arm64 chain is rebuilt on it) | drop in the 0.17 wave, keep the import check |
| aarch64 `__C_specific_handler` in `libkernel32.a` | leaked x86_64 entry (docs/10 2026-09-19) | upstream def unchanged (F_X64/F_ARM32 only); the dev `_mingw.sh` no longer leaks it — **measured**: `-lkernel32` ahead of the CRT now resolves to the private api set | `libcompat_arm64.a`'s redirect becomes redundant on 0.17; harmless to keep | drop in the 0.17 wave after `pe-resolve-imports.py` on the runner |
| aarch64 setjmp | fine (shim was a misdiagnosis) | **measured**: `__intrinsic_setjmpex` imported from the private api set, links | none | — |
| native win-arm64 zig | not planned on 0.16 | **exists on the dev track** (`zig_impl_win-arm64` in the win-arm64 subdir; `xc_host_valid` no longer excludes it) | a native win-arm64 chain on the `windows-11-arm` runner becomes possible, retiring the kappa cross lane | opportunity; wait for main label |
| `zig dlltool` / `zig ar` / `zig lib` | used | retained | none | — |
| activation contract (`ZIG_CC`, no `CC`) | — | unchanged (+ `SHIM_ZIG_TRIPLET`) | none | — |
| `-l:name`, 4-part sonames, `-Wl,-m` | rejected/odd | accepted | more CMake-generated link lines survive; we use none | — |

Contested after verification (one of two refuters disagreed, kept for the
record): Mach-O now sorts all link inputs by basename at flush time
(two same-named inputs would collide — none of our links has two); the
`extract-zig-crt.ps1` harvest of `zig cc -v` output may need its regex
re-checked against 0.17's lld spawn (the lld-link line is structurally the
same); and the 0.17 lld glue now emits `-l:/abs/path` with a basename
fallback SONAME for `-l`-resolved DSOs, which is the upstream fix for the
SONAME-less `DT_NEEDED` r-zig-pixi's shim works around.

Refuted (so not impacts): a libc++ 22 hardening/ODR-tag mismatch in our LLVM
links; a change in how the frontend finds libSystem; a new response-file
fallback for long Windows link lines (it existed in 0.16); any change in
compiler-rt symbol export from DLLs; the osx `zig ar` create failure being
new (it is a known 0.16 condition, already worked around).

## 3. Workarounds that may retire in the 0.17 wave, with the proof each needs

- `wcstold_compat.c` (four `build.bat`, `extract-zig-crt.ps1`): link
  `w.c` for `aarch64-windows-gnu` without the shim and check the import
  table shows `wcstold` from `api-ms-win-crt-convert-l1-1-0.dll` — **already
  true on the dev snapshot**.
- `csh_arm64.def` / `-lcompat_arm64`: link `csh.c -lkernel32` and check
  `__C_specific_handler` resolves to `api-ms-win-crt-private-l1-1-0.dll` —
  **already true on the dev snapshot**; confirm on the tag-based package and
  with `scripts/pe-resolve-imports.py` on `windows-11-arm`.
- `ZIG_LIB_DIR` mirror: **stays** (the feedstock patch is alive on 0.17).
- flang-rt's macOS target shim: **stays and matters more** (default 15.0).
- The six macOS LLVM build workarounds (ulimit, dsymutil off, libclang off,
  plugins off, AddLLVM.cmake sed, `-Wl,-rpath`): unchanged driver prongs;
  stay.

## 4. r-zig-pixi specifics (verified items only; the rest need their own pass)

- **build.zig does not compile on 0.17 (two blockers, both verified):**
  `b.install_prefix` is gone from `std.Build` (the prefix is parsed only by
  the make-phase process) — replace with a `-Dprefix=` option passed next to
  `--prefix`; `b.pathFromRoot` is gone — use `b.root.join(...)` +
  `toString`. ~38 interpolations of the prefix and 7 `pathFromRoot` sites.
- **Configure caching (must-change, verified):** `zig build` is split into a
  cached configurer; its cache key hashes only `-D`/release/target args, so
  env lookups (`CONDA_PREFIX`, `BUILD_PREFIX`, `SOURCE_DATE_EPOCH`), file
  reads (`subst.txt`, `config.h`), directory scans (`findFlangRt`) and
  `b.run(xcrun …)` results are reused silently across runs. Call
  `b.graph.poisonCache()` near the top of `build()` or register every input
  with `dependOnFileContents`/`dependOnDirectoryContents`.
- macOS target `os_version_min 13.0` still stamps 13.0 (an explicit min below
  the new 15.0 default is neither rejected nor clamped); framework linking
  moved into the frontend — test full/slim macOS variants.
- Unverified (credits ran out): `std.Build.Step.Run`/`Compile` were cut to a
  third of their size — expect API renames around `addOutputFileArg`,
  `addPrefixedDirectoryArg`, `setName`; PyPI `ziglang` 0.17.0 wheels will
  appear before conda-forge's main-label package, so the wheel path meets
  0.17 first; the `toolchain/zig-cc` SONAME injection becomes redundant.

## 5. Still unknown, and the cheapest experiment

- Whether the dev-track feedstock patches apply unchanged to the `0.17.0`
  tag (the snapshot predates it by days) — settled by the feedstock's own
  first tag-based build.
- Whether the regenerated 2.44 abilists keep every 2.17 symbol our chain
  uses — settled by the glibc ceiling tripwire in the first 0.17 llvm-zig
  build (10 min into stage 1).
- Whether a native `zig_impl_win-arm64` launches on `windows-11-arm`
  without declared `ucrt`/`vc14_runtime` deps — settled by one
  `windows-11-arm` job that installs it and runs `zig cc --version`.
- The mingw 15 CRT snapshot: whether `extract-zig-crt.ps1`'s file-name
  expectations (zigc.lib, api-ms-*.lib, compiler_rt.lib) hold — settled by
  the first flang-rt-zig win-64 build on 0.17.

## 7. Cross-check against the official release (2026-10-03)

The release notes (`ziglang.org/download/0.17.0/release-notes.html`) and
the official `x86_64-linux` tarball are out; conda-forge still has nothing
on its main label. Everything above survives; what the notes add or sharpen:

- **Toolchain:** LLVM/Clang/lld/libc++/libc++abi/libunwind **22.1.8**
  exactly; glibc 2.44 "available when cross-compiling" (the 2.17 target form
  is unchanged — probed on the official tarball: GLIBC_2.2.5 ceiling);
  macOS 27.0 headers; MinGW-w64 at commit `31bd54ab7d…` with "many functions
  now provided by zig libc rather than source files copied from MinGW-w64"
  (so CRT bugs go to zig's tracker, which matters for docs/12's drafts);
  `libc.txt`'s `gcc_dir` → `cc_dir`, now required on Linux (we pass none).
- **OS floors:** the std library's own minimum is **Darwin 15.0+**, Windows
  10+, Linux 5.10+. That is the origin of the 15.0 default we measured; an
  explicit lower `-target` for C code is still accepted (11.0 and 13.0
  measured on the snapshot).
- **Linkers:** the self-hosted COFF linker gained archives/implibs/TLS/
  `-gnu` ctors and the new ELF linker "remains disabled by default" — and
  `zig cc` for `*-windows-gnu` still spawns **lld-link** (official tarball,
  `-v`). No change to our Windows link path in this release.
- **Build system (r-zig-pixi):** the configurer/maker split and configure
  caching are headline features; the notes name the remedy exactly as §4
  says: `std.Build.Graph.poisonCache`, or `dependOnFileContents` /
  `dependOnFileMetadata` / `dependOnDirectoryContents` /
  `dependOnDirectoryMetadata`; `--cache-poison=disallowed` panics when a
  build.zig would poison the cache (useful in CI). Forking the build runner
  is no longer supported. Windows Run steps only extend PATH for `argv[0]`'s
  DLL directories now.
- **"Loop vectorization disabled" is about the Zig compiler's own pipeline,
  not `zig cc`:** probed — `zig cc -O2` emits packed FP ops for saxpy/dot
  on both 0.16 and 0.17 (4 packed ops; gcc -O3 gives 5, gcc -O2 none). No
  performance implication for R or our LLVM builds.
- **Official tarball probes (linux-64 host):** static libc++ (1,190
  `std::__1` symbols in a C++ hello, no libc++.so); aarch64-windows-gnu
  `wcstold` resolves from `api-ms-win-crt-convert`, `__C_specific_handler`
  from the private api set even with `-lkernel32` first, setjmp from the
  private api set; x86_64 keeps KERNEL32 for `__C_specific_handler` (correct
  there). So the two arm64 shims retire on **upstream** 0.17 too, not only
  on conda-forge's patched build. `zig env` prints `ZIG_LIB_DIR`.
- New tool: `zig objdump` (imports/exports/relocs for COFF, ELF, Mach-O) —
  a possible replacement for the Python PE parsers in `scripts/` once the
  pin moves.

Nothing in the notes changes §6's order: wait for the main-label package,
then one chain-wide wave.

## 8. What the feedstock's `dev` branch already absorbed (review received 2026-10-03, verified)

A separate review of the `dev` branch of the regular
`conda-forge/zig-feedstock` (0.17 master snapshots since spring, latest
merged bump `0.17.0-dev.2320+1e770dbef`, build 23200, published under the
`conda-forge/label/zig_dev` channel — the packages probed in §2 and §7)
lists how the feedstock copes with 0.17's build-system split. Checked
against the branch files; all three hold:

- **Maker-first argument order.** `recipe/building/_build.sh` splices
  `ZIG_MAKER_ARGS` (non-`-D` flags for `Maker.zig`: `--search-prefix`,
  `--maxrss`, `--verbose-link`, `-fqemu`, `--libc`) before `ZIG_PKG_OPTS`
  (`-D*` for the configurer); order now matters. Relevant to **r-zig-pixi**
  (`scripts/zig-build.sh` invokes `zig build`), not to flang-pixi, which
  never runs `zig build`.
- **Cache-dir contract.** `ZIG_GLOBAL_CACHE_DIR`/`ZIG_LOCAL_CACHE_DIR` are
  pinned under `$SRC_DIR` in the feedstock build, exported by activation
  (XDG → `$HOME/.local/share` → `$TMPDIR`), and the C wrappers now call
  `init_zig_global_cache_dir()` so a HOME-less env does not fail with
  `AppDataDirUnavailable` (absent from the 0.16 wrapper source). Our four
  build scripts already pin `ZIG_GLOBAL_CACHE_DIR` under `$SRC_DIR`
  (docs/17 §2, IMP-22); r-zig-pixi pins both under `BUILD_DIR`. Nothing to
  inherit beyond keeping that.
- **`lib/zig/compiler`, `build-web`, `init` are packaged** in `zig_impl_*`
  because `zig build` now compiles the maker/configurer from them on first
  use. Our `ZIG_LIB_DIR` mirror symlinks every entry of `lib/zig`, so it
  carries them; the same must stay true for r-zig-pixi's shim mirror (do
  not prune the mirror to `libc`/`libcxx`).
- Also on dev: `ZIG_LIB_DIR` is the feedstock's own bootstrap mechanism
  (`build.zig-03-compiler-step-zig-lib-dir.patch` sets `.zig_lib_dir` on
  the compiler step since `--zig-lib-dir` was removed) — the env var we
  rely on is load-bearing for them too, a good sign for its stability.

**Caveat checked:** the dev README names
`conda-forge/zig-feedstock-0.17-feedstock`, but no such repository exists
(GitHub 404; the org's only zig feedstock is `zig-feedstock`) and the
branch's `conda-forge.yml` still targets `main`. So whether 0.17 replaces
`main`'s 0.16 or lands as a separate feedstock/label is undecided on their
side; either way our trigger stays "a main-label `zig_impl_*` 0.17.0 that
`pixi` resolves from `conda-forge` without a label".


## 9. 0.17.0 on the main label (verified 2026-10-10)
